# Architecture

How the crates fit together, what each module owns, and the designs that span crates. `todo.md`
says *what* is still to do; this says *where and how*. Decisions with alternatives
are in `docs/decisions.md`.

## Crates and what they may use

```
humanart-core      nothing
humanart-math      humanart-core
humanart-io        humanart-core, humanart-math
humanart-model     humanart-core, humanart-math, humanart-io                      no GPU
humanart-doc       humanart-core, humanart-math, humanart-io, humanart-model            no GPU
humanart-gpu       humanart-core, humanart-math, wgpu
humanart-shaders   humanart-core, humanart-gpu, wgpu (naga)
humanart-render    humanart-core, humanart-math, humanart-io, humanart-model, humanart-gpu, humanart-shaders     not humanart-doc
humanart-ui        humanart-core, humanart-math, humanart-io, humanart-gpu, humanart-shaders               not humanart-model, not humanart-render
humanart-tools     humanart-doc, humanart-render and below
humanart-capture   humanart-doc and below (no GPU required)
humanart-agent     humanart-doc, humanart-render, humanart-tools, humanart-capture and below
humanart-runtime   humanart-core, humanart-math, humanart-io, humanart-model, humanart-gpu, humanart-shaders, humanart-render
humanart-platform  humanart-core; native only
humanart       everything + winit      (binary `humanart`)
humanart-cli       everything headless     (binary `humanart-cli`)
```

The ten crates from `humanart-core` to `humanart-runtime` except `humanart-tools`, `humanart-capture`, `humanart-agent` compile for
`wasm32-unknown-unknown`: they reach files, clocks, threads and entropy only through the traits in
`humanart_core::platform`. The native implementations of those traits live in `humanart-platform`; tests and wasm
use `MemoryFs`, `ManualClock` and `InlineSpawner` from `humanart-core`.

## Data flow of one edit

1. Input reaches the UI (`humanart-ui`), which calls application code in `humanart`.
2. The application (or the agent server, or a script) builds a **command** (`humanart-doc`) and posts it to
   the command queue. The document has one writer: the queue's owner on the main thread.
3. Applying a command validates it (locks, protection, ranges), mutates the document, appends it to
   the journal, records history, and emits a notification event with a sequence number.
4. The document publishes an **evaluation input snapshot**: a small POD block (the parameter vector
   resolved to model weights, expression weights, joint rotations, layer versions and dirty flags)
   defined in `humanart-model`, so `humanart-render` and `humanart-runtime` consume it without knowing `humanart-doc`.
5. The renderer diffs the snapshot against the last one and re-evaluates on the GPU only what
   changed (`[EVAL-03]`), re-resolves only dirty skin rectangles (`[SKN-02]`), regenerates only dirty
   grooms, and draws.
6. Readbacks (picking, metrics, screenshots, agent renders) come back through the readback ring one
   or more frames later (`[PERF-R3]`).

The **engine** that ties document, model, renderer and tools together without a window lives in
`humanart-agent` (`Engine`): the editor, the CLI and the MCP server all drive the same engine, which is how
headless renders match the editor's (`[AC-WP23-3]`). As built: `engine::Viewer` binds the surfaced
skin look once at creation (`engine::skin::SkinLook`: zone masks, compositor, micro-detail and
`humanart_render::surface::SkinSurface` at group 3 of the geometry pass, ADR-052), and
`humanart-cli render` (`crates/cli/src/render.rs`) drives the same `Viewer` offscreen. A slider drag
goes through `humanart_doc::session::Session::drag_scalar`, which folds the frame into the open
gesture without allocating; the engine syncs on the event sequence and `Session::revision()`.

## The template (ADR-006)

The template is generated by code in `humanart-model::generate`; nothing is drawn by hand or imported.

- **Topology** comes from a quad-mesh builder with a few operations that keep every face a quad:
  cylinder grids (torso, neck, head, limbs, fingers), grid caps that close a loop, **O-grid inserts**
  that replace a rectangular block of quads by concentric rings around a hole (eyes, mouth, nostrils,
  ears, limb roots: this is what gives edge loops around the features and the rows across the
  eyelids `[MOD-01]`), loop extrusion (eyelid thickness, lip interior, the mouth bag, sockets) and
  bridges. Catmull-Clark subdivision refines the cage.
- **Geometry** comes from anatomical shape functions evaluated at each vertex's parametric address
  (which part, which ring, which angle): generalised cylinders along spine curves with profile
  functions for the body, a radial function with feature terms for the skull and face, local polar
  shapes for eyelids, lips and ears, followed by tangential relaxation.
- **Everything else is derived from the same parametric addresses**: regions, UV tiles and seams,
  landmarks (as barycentric points), the skeleton and the skin weights.
- **Identity axes and expression targets** are authored as *delta fields*: data files that describe a
  target as a sum of primitives (a region or landmark anchor, an anisotropic falloff, a displacement
  in the local surface frame). The builder evaluates the fields on the template into the sparse delta
  bases of `[EVAL-02]`. When captured data exists, the statistical model builder writes the same
  bases from scans, and nothing downstream changes (`[ID-07]`).
- **As built**, both are authored in code rather than data files: identity components in
  `humanart_model::identity` (`build`, `add_components`, `with_identity`; 62 components bound by
  name to the registry's `component` parameters through `identity::BINDINGS`, all
  `DeltaKind::Semantic`, ADR-048), expression targets in `humanart_model::expression` (ADR-043).
  `generate::build::template` applies them before the LODs are generated, so every LOD carries the
  deltas (wiring verified by template-gen in round 6; `identity::without_identity` strips the
  identity components again, for tests that rebuild them). Body measurements come from
  `data/anthropometry/ansur2.json` (ADR-046; `generate/anatomy.rs` cites the variable ids, tests
  `anat_01` / `anat_02`); `identity::measure` measures the template like a tape and calibrates the
  identity axes to one SD per unit (ADR-051). Skin weights: `generate::rig::skin` (ADR-049).

The generated template is written as `data/template/template.antmpl` by `humanart-cli build-template`; the
rest of the system reads only that package (`[MOD-02]`).

## Text and fonts

`humanart-io::ttf` parses the fonts; `humanart-ui::fontbake` turns outlines into a multi-channel signed distance
field atlas plus metrics and kerning (`.anfont`), run offline through `humanart-cli fontbake` and
`tools/fontbake/`; the baked files are shipped in `data/fonts/` and loaded at start (`[UI-03]`). The
reference application rasterises coverage bitmaps at run time instead; the specification requires the
baked distance-field path, so text is the one place where the UI plumbing deliberately differs from
the reference.

## Shaders

All WGSL is under `shaders/`, embedded by `humanart-shaders` and composed by its preprocessor (`#include`,
`#ifdef` on capability flags). Quality variants are `override` constants specialised at pipeline
creation (`[PERF-R5]`). Every file is in the manifest and validated by naga in tests; library
functions have CPU references and are compared on a real device.
