# Decisions (ADR log)

Every non-trivial choice, its alternatives and the reason (spec 0.3). Newest last. An ADR is never
rewritten: a later ADR supersedes it and says so.

## ADR-001: Third-party crates are `wgpu` and `winit` only

- **Context.** `[DEP-01]` allows `wgpu`, the reference application's windowing crate, and "whatever the
  reference application already uses for the same job". AtroxaBot uses `winit` 0.30.13 and `wgpu`
  30.0.x, and also `serde`, `serde_json`, `bytemuck`, `png`, `zune-jpeg`, `image-webp`, `flate2`,
  `ttf-parser`, `arboard`, `ureq`, `cpal` and `ring` (`atroxabot-app/Cargo.toml`).
- **Decision.** Only `wgpu` (30.0.x, the reference's major version) and `winit` (0.30.x). Every other
  crate the reference uses is either forbidden by name in `[DEP-02]` (`serde`, `serde_json`,
  `bytemuck`, `png`, `arboard`) or has a mandatory in-house replacement in `[DEP-05]` (`ttf-parser`,
  `zune-jpeg`, `flate2`), or serves a job HumanArt does not have (`ureq`, `cpal`, `ring`,
  `image-webp`). The owner's instruction for this build says the same: no filler crates.
- **Difference from the reference (REF-02).** The reference casts POD data with `bytemuck` and parses
  fonts with `ttf-parser`; HumanArt uses its own `Pod` trait in `humanart-gpu` `[UNS-03]` and its own
  TrueType parser in `humanart-io`.
- **Alternatives.** Following the reference's list where `[DEP-01]` could be read to allow it: rejected,
  the explicit list in `[DEP-02]` and the in-house list in `[DEP-05]` are the more specific rules.

## ADR-002: Toolchain, edition and lints follow the reference

- **Decision.** Rust 1.99.0 pinned in `rust-toolchain.toml` (the stable toolchain installed where the
  reference is built), edition 2024, resolver 3, and the reference's lint table (`clippy::pedantic`
  warn, `missing_docs` warn, `unsafe_op_in_unsafe_fn` deny) with these additions: `unwrap_used`,
  `expect_used`, `todo`, `unimplemented` and `dbg_macro` are denied (`[ERR-03]`, spec 0.1.6), and a
  few pedantic lints that fight numeric code are allowed (`many_single_char_names`, `similar_names`,
  `float_cmp`, `cast_lossless`, `too_many_arguments`, `missing_errors_doc`, `must_use_candidate`,
  `return_self_not_must_use`, `inline_always`).
- **Profiles.** `release` is the reference's plus an explicit `opt-level = 3` `[PERF-R7]`; `profiling`
  inherits it with symbols. `dev` builds our crates at `opt-level = 1` and dependencies at 3, because
  codec, solver and fuzz tests are too slow unoptimised (the reference optimises dependencies only).

## ADR-003: The repository root is the workspace root; `shaders/` is a real directory

- **Context.** Spec 3.1 shows `humanart/` as the root and `shaders/` as "symlink or path used by
  humanart-shaders".
- **Decision.** The workspace root is the repository root. `shaders/` is a plain directory there, the
  single source of truth; `humanart-shaders` embeds the files with `include_str!("../../../shaders/...")`.
  No symlink: symlinks need special rights on Windows and do not survive every git checkout.

## ADR-004: `humanart-ui` depends on `humanart-gpu` and `humanart-shaders`, not on `humanart-render`

- **Context.** Section 3.2 writes the chain as `(humanart-gpu ← humanart-shaders ← humanart-render) ← humanart-ui`, and in the
  same paragraph says `humanart-ui` must not depend on the character model. `humanart-render` depends on
  `humanart-model` (it draws the model, and `humanart-runtime` is listed as depending on both).
- **Decision.** `humanart-ui` depends on `humanart-core`, `humanart-math`, `humanart-io` (font atlas and PNG loading),
  `humanart-gpu` and `humanart-shaders`. The application composes the UI pass after the renderer's passes. This is
  the only reading under which both sentences hold.

## ADR-005: `humanart-core` denies unsafe code crate-wide and allows it in `alloc` only

- **Context.** `[UNS-01]` lets `humanart-core::alloc` use unsafe; a crate-level `forbid` cannot be relaxed
  for one module.
- **Decision.** `humanart-core` carries `#![deny(unsafe_code)]`; the `alloc` module alone has
  `#[allow(unsafe_code)]` (the counting global allocator used by the zero-allocation tests `[PERF-R1]`
  needs `unsafe impl GlobalAlloc`). `tools/check-tree.sh` fails if `unsafe` appears anywhere else in
  the crate. Every other crate except `humanart-gpu` and `humanart-platform` carries `forbid`.

## ADR-006: The template is authored in-house, procedurally

- **Context.** `[MOD-02]` allows an audited external base or an in-house base; `[LIC-03]` requires the
  audit to cover the model assets and Appendix F makes the in-house template the default when the
  audit is inconclusive. No external base was supplied with the task, and no audit of one has been
  done by a person with authority over licences.
- **Decision.** The template is generated by code in `humanart-model` (`[LIC-02]` (c), procedurally generated
  data): topology, regions, UVs, landmarks, skeleton, skin weights, expression targets and identity
  axes all come from the generator, so the provenance is the source code. The Template Adapter
  (`humanart-capture`) produces the same `.antmpl` package from an external base, so an audited base or a
  scanned one can replace the generated template without code changes `[ID-07]`.
- **Consequence.** The realism of forms is bounded by what the generator and the authored deltas
  express until captured data (section 11) replaces them. This is recorded in `docs/blockers.md`.

## ADR-007: `humanart-io` codecs are cargo features, all on by default

- **Decision.** Each codec family in `humanart-io` is behind a feature (`json`, `deflate`, `png`, `jpeg`,
  `hdr`, `exr`, `ktx2`, `gltf`, `obj`, `ply`, `ttf`, `lz`, `bc`, `mip`), all in `default`; the
  `humanart-math` modules (`linalg`, `solve`, `color`) likewise. The runtime can then be built with only
  the codecs a game needs, and a codec's tests can be run alone. In place since 2026-11-19.

## ADR-008: wgpu backends are selected per target

- **Decision.** The workspace declares `wgpu` with `std` and `wgsl` only; each crate that uses it adds
  `dx12`, `metal`, `vulkan`, `gles` on native targets and `webgpu` on `wasm32` through target-specific
  dependency tables. The reference lists the four native backends unconditionally because it has no
  wasm build; this is the minimal change that satisfies `[PLAT-03]`.

## ADR-009: Windows builds link the C runtime statically

- **Decision.** `.cargo/config.toml` sets `-C target-feature=+crt-static` for `cfg(all(windows,
  target_env = "msvc"))`, as the reference application does. Without it the exe needs
  `VCRUNTIME140.dll` from the Visual C++ Redistributable, which a fresh Windows does not have, and
  there the app does not start at all. Local builds, tests and CI all read the same file.

## ADR-010: The JSON parser is strict where RFC 8259 leaves a choice

- **Context.** RFC 8259 lets a parser decide what to do with duplicate object keys, `\u` escapes that
  are not a Unicode scalar value, numbers outside the range of the implementation and a leading byte
  order mark. Documents, templates, agent tool calls and settings all go through `humanart_io::json`.
- **Decision.** Every one of them is an error, with the byte offset, line and column:
  - an object with two members of the same key (every way of resolving it silently loses data);
  - a lone or unpaired surrogate in a `\u` escape (it has no UTF-8 form);
  - a number that rounds to infinity in an `f64` (`1e400`): the document model has no infinity and
    the writer never emits one; integer literals that fit `i64` / `u64` stay exact integers.

  One UTF-8 byte order mark at the very start is skipped, as RFC 8259 allows; one anywhere else,
  or a second one, is an error. The writer never emits one.
  No comments, trailing commas, single quotes, `NaN` / `Infinity` or control characters in strings
  either. The writer refuses NaN and the infinities.
- **Implementation state (2026-11-19).** All of it is implemented and tested
  (`crates/io/src/json/parse.rs`, `number.rs`, the reject set in `json/tests.rs`; the BOM cases in
  the tests of `parse.rs`).
- **Alternatives.** Last-key-wins for duplicates (what most libraries do): rejected, a hand-edited
  document with a repeated key would lose a value without a word. Replacing lone surrogates with
  U+FFFD: rejected for the same reason. Rejecting a BOM: rejected, a settings or theme file saved by
  a Windows editor often starts with one, and skipping it loses nothing.

## ADR-011: EXR support is single-part scan-line files

- **Context.** `[IO-03]` asks for scan-line EXR reading and writing (bakes, AOVs, HDR environment
  maps). OpenEXR also has tiled, multi-part and deep files, sub-sampled channels and lossy codecs.
- **Decision.** `humanart_io::exr` reads and writes single-part scan-line files with NONE, RLE, ZIPS,
  ZIP and PIZ compression, `uint` / `half` / `float` channels with any names (at most 1024), any data
  window and all three line orders; unknown attributes are kept. The writer defaults to ZIP, sorts
  channels by name and is deterministic. Tiled, multi-part and deep files, sub-sampled channels and
  PXR24, B44, B44A, DWAA and DWAB return `Error::Unsupported`; nothing is guessed.
- **Evidence and limits.** Six ffmpeg-written fixtures decode bit-exactly; ffmpeg's independent
  decoder reads all 30 of our encodes (5 compressions x half/float x Y/RGB/RGBA) to our samples
  (dev-time cross-check). PIZ is verified by round trip and by ffmpeg reading our PIZ files only: no
  PIZ file written by the reference OpenEXR library is available (`docs/blockers.md` B-005).
- **Half floats.** The codec uses `humanart_math::F16` (io enables math's `linalg`); the private copy
  the EXR agent wrote was removed by the lead.

## ADR-012: The LZ compression codec is an in-house frame format, not LZ4

- **Context.** `[DEP-05]` requires an in-house fast compression codec (`.antmpl` payloads, KTX2
  supercompression of our own files, caches).
- **Decision.** `humanart_io::lz`: LZ4-style sequences in blocks of 2^16 .. 2^22 bytes inside an
  own frame (magic `HALZ`, version 1, u64 content size, a per-block word with a stored bit, a
  MurmurHash3 fold64 checksum of the content, no trailing data). The format is specified byte by byte
  in `docs/format-lz.md`. The decoder is bounds-checked safe Rust; the content size is checked against
  `Limits::max_bytes` and against 256 x the frame length before anything is allocated.
- **Alternatives.** Byte compatibility with the LZ4 frame format: not claimed and not tested, since
  HumanArt has no LZ4 files to read and the LZ4 frame has options we would have to support for no
  gain. Unchecked copies (LZ4 reaches about 3 GB/s with them): rejected, `[UNS-01]` keeps unsafe out
  of `humanart-io`; the safe decoder measures about 1.2 GB/s on text.

## ADR-013: PNG files carry HumanArt's colour space in a tEXt chunk

- **Context.** A PNG cannot say "normal map" or "data, never colour-convert". `[COL-01]` needs every
  texture's colour space known at load time.
- **Decision.** The decoder decides the colour space in this order: a `tEXt` chunk with the keyword
  `HumanArt colour space` (written by our encoder for `Normal` and `Data` images), then `sRGB` or
  `iCCP` (sRGB), then `gAMA` of 1.0 within 5 % (linear), otherwise sRGB. The encoder writes `sRGB` +
  `gAMA` 1/2.2 for sRGB images, `gAMA` 1.0 for the others, plus the tEXt tag for normal and data
  images. ICC profiles are detected and treated as sRGB, not interpreted; `cHRM` is reported in
  `Info` only.
- **Alternatives.** Inferring data from file names or channel counts: rejected, it guesses.
  Interpreting ICC profiles: a colour-management engine is out of scope for the codec, so an image
  with a non-sRGB ICC profile is read as if it were sRGB (a known limit of the decoder).

## ADR-014: Small fixed-size matrices in `solve` and `color` are row-major arrays

- **Context.** The `linalg` types (`Mat3`, `Mat4`, ...) are column-major (`cols`), like WGSL. The
  solvers and the colour code also need 3x3 matrices, and their sources (colour-science papers,
  numerical-analysis texts) write them row by row.
- **Decision.** `humanart_math::solve` (`svd3`, `symmetric_eigen3`, `kabsch`, ...) and
  `humanart_math::color` (`ColorMatrix = [[f64; 3]; 3]`) use plain arrays indexed `m[row][col]`, so
  published constants are copied as printed. They are independent of `linalg` (each feature builds
  alone). Code that moves such a matrix into a `linalg` type or onto the GPU converts it explicitly
  at that boundary; the GPU only ever sees the column-major `linalg` types.
- **Alternatives.** One column-major convention everywhere: rejected, every published colour matrix
  would have to be transposed by hand, which is where copying errors come from.

## ADR-015: Job closures are `'static`; there are no borrowing (scoped) parallel loops

- **Context.** `[THR-01]` asks for a job system. A scoped `parallel_for` that lends `&mut` slices to
  worker threads needs `unsafe` lifetime erasure, and ADR-005 confines `humanart-core`'s unsafe code
  to `alloc`.
- **Decision.** `humanart_core::jobs` takes `'static` closures (`spawn`, `parallel_for`,
  `parallel_map`); data reaches workers through `Arc` or by value and comes back through
  `JobHandle` / `parallel_map`'s ordered `Vec`. Waiting threads run queued jobs, so nested spawns and
  nested loops cannot deadlock. With zero threads (wasm single-thread, `Jobs::inline()`) everything
  runs on the caller. A panicking job gives `JobError::Panicked` and the worker survives.
- **Alternatives.** Scoped loops through `std::thread::scope`: spawns OS threads per call, which the
  steady-state frame budget forbids and wasm cannot do. Scoped loops on the pool: need unsafe outside
  `alloc`, a separate ADR if ever wanted.

## ADR-016: `humanart-gpu` tests use small inline WGSL compute shaders

- **Context.** Shaders live under `shaders/` and are listed in the `humanart-shaders` manifest. The
  GPU crate's own tests (uniform ring, readback, profiler, recovery, the steady-state loop) need a
  shader to run, but `humanart-shaders` depends on `humanart-gpu`, so the GPU crate cannot use it.
- **Decision.** Tests in `humanart-gpu` (inside `#[cfg(test)]` only) may hold short WGSL compute
  shaders as string literals. No non-test code in the crate contains WGSL. Every shader the product
  runs still comes from `shaders/` through the manifest.
- **Alternatives.** Moving those tests into `humanart-shaders` or `humanart-render`: rejected, the
  ring, readback and recovery behaviour would then be tested far from its code and only after the
  shader foundation exists.

## ADR-017: GPU device loss is recovered from CPU state; caches are reset, not replayed

- **Context.** `[ERR-05]`: a lost device must not lose the user's work, and the app must come back.
- **Decision.** CPU-side state is the source of truth. `Recovery::check` notices a lost device (one
  atomic load per frame), recreates it, and calls `Rebuild` on every registered GPU object
  (`Resources`, `UniformRing`, `ReadbackRing`, `GpuProfiler`, `StreamingPool`, `PipelineCache`), which
  re-create their buffers and textures and re-upload from their CPU copies. The pipeline cache cannot
  rebuild pipelines itself (descriptors borrow modules and layouts), so it is emptied and its owner
  re-runs the same pre-warm. After `MAX_ATTEMPTS` (8) frames without a device the error is returned
  to the app. No driver-level `wgpu::PipelineCache` (Vulkan-only) is used.
- **Evidence.** `recovery::tests::ac_wp04_2_a_lost_device_is_rebuilt_and_refilled_from_cpu_state`
  destroys a real device and gets the same compute result and texels on the new one.

## ADR-018: Native shims are Windows-first; other systems fall back in-app

- **Context.** WP-31 asks for per-OS file dialogs, clipboard, DPI and pen input with no crate beyond
  `wgpu` and `winit` (ADR-001), reusing the reference app's solutions.
- **Decision.** `humanart-platform` calls the OS directly: on Windows the COM file dialogs on their
  own STA thread, the `CF_UNICODETEXT` clipboard (CRLF <-> LF, 64 MiB limit), `GetPointerPenInfo` for
  tilt, rotation, eraser and barrel button next to winit's touch events, and `BCryptGenRandom`.
  On Linux and macOS the clipboard is in-process only and dialogs return `Unavailable`; the app then
  shows its own picker (the reference app's zenity / kdialog / osascript helpers are the route to
  add them). DPI comes from winit (per-monitor v2, `ScaleFactorChanged`); no shim. Every shim can be
  disabled (`Shims::disabled()`), and each then reports `Disabled` so the in-app fallback runs.
- **State.** Windows built and tested; Linux and macOS code is type-checked by clippy only, never
  linked or run (`docs/blockers.md` B-003).

## ADR-019: The character document is sections of `key = <compact JSON>` lines; every change is a list of text edits

- **Context.** `[DOC-21]` needs a diff-friendly, hand-parsed, byte-stable document format; WP-08 needs
  forward and inverse payloads for every command and conflict detection between them.
- **Decision.** A `.anthropos` document is a header plus `[kind key]` sections whose entries are
  sorted by key, one `key = <value>` line each, values in strict compact JSON (ADR-010), written by
  one canonical writer (`crates/doc/src/text.rs`, grammar in `docs/format-anthropos.md`).
  `text::Edit` (set an entry, insert a section, remove a section, each carrying the expected
  before-value) is the universal change unit: `diff`, `apply` (atomic, `Conflict` on a mismatch) and
  `invert`. `Document::apply_edits` rejects a result that is not canonical, so an inverse is exact.
  The current weights of `[DOC-05]`..`[DOC-07]` and `[DOC-09]` are registry parameters, not separate
  structures.
- **Alternatives.** A pretty-printed JSON document: rejected, nested diffs and no stable line
  granularity. Typed per-command payloads only: rejected, every new command kind would need its own
  inverse and conflict logic.
- **Evidence.** `crates/doc` tests: `text` 3000-case diff property test, `document` 200-case
  diff/apply/invert property test, fixture `crates/doc/tests/fixtures/document-v1.anthropos`
  reproduced byte-identically (doc agent's STATUS; not rerun by the integrator because another agent
  is editing `humanart-doc`).

## ADR-020: Blobs are content-addressed `HABL` files

- **Decision.** Bulk document data lives in `blobs/<content hash>` beside the document: a 16-byte
  header with magic `HABL`, then the content, optionally as one LZ frame (ADR-012). The file name is
  the hash of the content, so equal content is stored once and a changed byte is detected on read
  (`blob` tests: every-byte-flip detection). Empty content is the zero hash, meaning "no blob", and
  is never written. Unreachable blobs are removed by `BlobStore::collect_garbage` using the set
  `blob::reachable` computes over the open documents. Layout in `docs/format-anthropos.md`.
- **Alternatives.** Blobs embedded in the text document: rejected, it would break the line-based
  diffs of ADR-019.

## ADR-021: The LOD generator collapses half-edges onto LOD0 vertices; budgets are enforced by measurement

- **Context.** `[MOD-05]` / `[AC-WP28-1]`: LODs must carry every attribute (UVs, regions, skin, deltas,
  landmarks) and stay within declared error budgets.
- **Decision.** `crates/model/src/simplify/` uses half-edge collapse (the kept vertex is an LOD0
  vertex, as in meshoptimizer) ordered by Garland-Heckbert plane quadrics plus Hoppe UV attribute
  quadrics. Every LOD vertex is therefore an LOD0 vertex: sources are the identity and every
  attribute transfers exactly. Borders, UV seams, hard edges, part and region boundaries and
  caller-given protected loops (eyelids, lips) are feature edges along which vertices may only slide.
  Budgets are checked by measuring every welded LOD0 vertex against the level, not by trusting the
  quadric estimate; a level over budget is rolled back by bisecting its collapse list (steps of
  1/64) and replaying the longest valid prefix.
- **Alternatives.** Placing the kept vertex at the quadric optimum: rejected, attributes would have
  to be re-interpolated and the skin and delta transfer would no longer be exact.
- **Open.** `LodLevel` has no per-level landmarks (`GeneratedLod::landmarks` carries them). The lod-gen
  agent proposes adding `landmarks` to `LodLevel` and to the LODS package section if the runtime
  needs them per LOD; not decided.
- **Amended by ADR-045** (round 5): budgets are enforced per collapse by measurement, the bisection
  is only a safety net, and every level is a valid UV layout.

## ADR-022: glTF errors reuse the `humanart-io` error; JSON-tree problems carry offset 0

- **Decision.** `humanart_io::gltf` returns the crate's `Error`. Problems found in the parsed JSON
  tree are `Error::Invalid { offset: 0, what }` with `what` naming the member, because the JSON tree
  keeps no byte positions.
- **Alternatives.** Byte positions on every JSON value: not done, it would grow every `Value` for the
  sake of error messages. The same limitation shows in `Ply::to_mesh` (PROGRESS open issues).

## ADR-023: KTX2 files use a private supercompression id for the in-house LZ codec

- **Decision.** `humanart_io::ktx2` supports supercompression none, ZLIB (scheme 3, only with feature
  `deflate`) and the in-house LZ codec (ADR-012) under the private scheme id `0x5A4C4148` (the bytes
  `HALZ` read little-endian, `ktx2::SCHEME_LZ`), one LZ frame per mip level. In the DFD of a
  supercompressed file `bytesPlane0` is 0; the reader accepts 0 or the block size. BasisLZ,
  Zstandard and `VK_FORMAT_UNDEFINED` return `Unsupported`.
- **Consequence.** LZ-supercompressed KTX2 files are readable only by HumanArt; files meant for other
  tools must be written uncompressed or with ZLIB.
- **Not verified.** DFD `sampleLower` / `sampleUpper` for block formats follow KTX-Software
  conventions as the io-gltf agent recalled them; `ktx validate` is not installed on this PC, and the
  reader does not check those two words.

## ADR-024: JPEG support is 8-bit Huffman baseline and progressive; the rest is refused

- **Decision.** `humanart_io::jpeg` decodes baseline and progressive 8-bit Huffman-coded files and
  encodes baseline JFIF (IJG quality scaling, Annex K Huffman tables, 4:4:4 or 4:2:0, grey).
  Arithmetic coding, 12-bit, lossless, hierarchical, two-component frames and DNL heights return
  `Unsupported` (`[IO-02]` does not ask for them). A truncated scan is an error, never a partial
  image; a missing EOI is `Truncated`.
- **Alternatives.** Returning the decoded part of a truncated file: rejected, a file that loads
  half-grey without an error hides the damage.

## ADR-025: BC7 normal maps carry roughness in alpha

- **Decision.** The GPU BC7 encoder (`humanart_render::compress`) stores a normal map as RGB =
  n * 0.5 + 0.5 with roughness (adjusted per mip by `humanart_io::mip`'s vMF/Toksvig rule) in alpha.
  `Bc7Options::normal_xy` drops blue's error weight for shaders that rebuild z from x and y; the
  texture agent measured only a small gain on its test map (mean angular error at Normal quality
  1.27 degrees for xyz, 1.24 for xy + rebuilt z).
- **Alternatives.** A two-channel normal texture plus a separate roughness texture: one more texture
  per material.

## ADR-026: UI primitives are instances read from a storage buffer

- **Decision.** `shaders/ui/quad.wgsl` reads one 112-byte instance per primitive from a read-only
  storage buffer by `instance_index`, not from vertex attributes, because the shader manifest's
  device validation builds pipelines without vertex buffers. Each instance carries its clip
  rectangle, so clips never split batches: a frame without images is one draw call (measured: 6000
  primitives under 200 clips, one call).
- **Alternatives.** Vertex-buffer instancing: would need a special case in the manifest validator.
  Scissor rectangles per clip: one draw call per clip change.

## ADR-027: UI text is an MSDF atlas baked offline

- **Decision.** Fonts are baked at development time by `tools/fontbake/bake.sh`
  (`humanart_ui::fontbake`: multi-channel signed distance fields with Chlumsky edge colouring) into
  `.anfont` files (format in the doc comment of `crates/ui/src/font.rs`). The fallback glyph is the
  font's U+FFFD, else `.notdef`, stored under U+FFFD. Glyphs are placed at subpixel x with
  pixel-snapped baselines; text gets stem darkening of 0.12 px at 9 px, fading to 0 at 16 px. Complex
  shaping and bidirectional text are out of scope.
- **Alternatives.** Rasterising glyphs at run time per size and scale: needs a rasteriser in the
  runtime and an atlas page per size.

## ADR-028: UI interaction uses last frame's rectangles; painting is deferred

- **Decision.** The immediate-mode `Ui` hit-tests against the clipped rectangles of the previous
  frame (topmost layer, then last registered, wins) and records paint commands in widget-relative
  geometry (`Area` / `Anchor`) that is resolved after this frame's layout.
- **Alternatives.** Laying out before interacting (two passes per frame): doubles the build work.

## ADR-029: The journal records exact edits; selective undo is a new history entry

- **Decision.** Every journal record (`humanart_doc::save::Record`, format in
  `docs/format-anthropos.md` section 5.1) carries the exact text edits it made, so replay depends on
  nothing but the saved text and never re-resolves a command against the registry. The history stays
  linear: "undo my last" / "undo the agent's last" of an entry that is not on top is recorded as a new
  entry of kind `undo` that names the entry it reverts (`Entry::reverts`), and is allowed only when
  no later applied entry touches the same targets `[CMD-04]`; the revert itself can be undone. Undo,
  redo and accept are checked by the lock policy like commands, for the requesting author (an agent
  cannot undo a human's command while protection is on, `[LOCK-02]`). Command and proposal ids left
  NIL are derived from a per-session seed and a counter; the host passes a fresh random seed per
  session, tests pass fixed seeds.
- **Alternatives.** Journaling the commands and resolving them again on replay (rejected: replay
  would then depend on more than the saved text). A branching undo tree (rejected: `[CMD-04]`
  describes one shared history).
- Source: `target/agents/commands/STATUS.md`, module docs of `crates/doc/src/save.rs` and
  `crates/doc/src/history.rs`.

## ADR-030: The identity prior is block-diagonal by groups; plausibility is a chi-square tail probability

- **Decision.** `humanart_model::eval::prior::IdentityPrior` treats its groups of identity
  components as independent (a mean and a diagonal or full covariance per group). The [0, 1]
  plausibility score `[ID-04]` is the chi-square survival function `P(χ²_k > d²)` of the Mahalanobis
  distance `d²` with `k` retained components, so samples of the prior score uniformly on [0, 1] and
  the warning threshold 0.2 (`WARNING_THRESHOLD`; it never blocks) warns for 20 % of them. Sampling
  `[ID-06]` draws one RNG stream per group. With no groups the prior is the no-data prior `[ID-07]`.
- **Alternatives.** None recorded by the eval-cpu agent.
- **Not decided here.** No real statistics exist (B-001): every test uses synthetic covariances; the
  file the model build `[STAT-08]` writes (`identity-prior.json` or a package section) is not
  defined yet.
- Source: `target/agents/eval-cpu/STATUS.md`.

## ADR-031: Rig logic and the joint hierarchy evaluate on the CPU

- **Decision.** The rig logic `[EXP-03]` (`humanart_model::eval::rig::RigGraph::evaluate`) and the

- Source: `target/agents/gpu-eval/STATUS.md` (proposed ADR).

## ADR-032: GPU deformation outputs are packed f32 xyz, not the `[EVAL-05]` example layouts

- **Decision.** The deformer's output buffers are positions, previous positions and normals as
  packed `f32` xyz (the `GpuScene` stream layout of `humanart-render`), tangents as `vec4<f32>`
  (w = handedness), region strain as `vec2` per region and a per-vertex strain buffer. `[EVAL-05]`
  names `vec4<f32>` position + region-id bits, `vec4<f16>x2` normal/tangent or octahedral encoding
  as its layouts; none of them is used.
- **Reason.** The renderer can bind the deformer's buffers in place of its own position /
  previous-position / normal streams without a copy or a second vertex-pulling path.
- **Consequences.** More bytes per vertex than the octahedral or f16 layouts (bandwidth not
  measured against them). The deformer is not wired into the renderer yet (row 10 / 11 of
  `PROGRESS.md`): the zero-copy claim of `[EVAL-05]` is a design, not yet evidence.
- Source: `target/agents/gpu-eval/STATUS.md`, `target/agents/render/STATUS.md`.

## ADR-039: The base template is an anatomically complete human

## ADR-040: wgpu instance and device creation and drop are serialised; test binaries share one device

- **Context.** The render acceptance binary sometimes stalled under GPU contention (row 11 of
  `PROGRESS.md`). The skin-shading agent reproduced it (1 of 23 runs) and took stacks with lldb: a
  loader-lock deadlock inside the NVIDIA driver (`nvoglv64.dll`), not a wait on the GPU. A test
  thread exiting holds the Windows loader lock (thread-detach in the driver's `DllMain`) and spins on
  a driver lock, while another thread inside `vkCreateDevice` holds that driver lock and waits for
  the loader lock; wgpu's GL backend enumerating adapters (`wglMakeCurrent`) and new threads then
  block too. The trigger was every test creating and dropping its own `Gpu` on its own thread,
  concurrently with test threads exiting. No poll timeout can end it.
- **Decision.** `humanart_gpu::LifecycleGuard` (`crates/gpu/src/lifecycle.rs`, a process-wide
  binary lock; a no-op on wasm32) is held while `create_instance` and `Gpu::new` create the
  instance, adapter and device (and drop them on failure), and while `impl Drop for Gpu` drops them.
  `humanart_gpu::shared_headless()` gives one `DeviceRequest::default()` device per process, never
  dropped, its failure remembered; `testing::gpu()` and the app tests use it. `Gpu::headless` on
  native tries the primary backends first (no GL instance, so no hidden window or WGL context) and
  falls back to all backends on `NoAdapter`; `WGPU_BACKEND` still overrides. The render integration
  tests (`crates/render/tests/common`) create one device per binary (`OnceLock`) and run a watchdog
  that aborts the binary after 300 s without progress. Blocking GPU waits in `humanart-render` are
  bounded (`capture::wait_for_submission`, `GPU_WAIT_LIMIT` 60 s, `RenderError::GpuTimeout`).
- **Evidence.** Before: 1 of 23 acceptance runs deadlocked (skin-shading agent, `stress2/`). After
  the render-test fix: 48 of 48 acceptance runs in parallel with the other render binaries, no cap
  hit (`stress3/`). After the lifecycle lock: 10 rounds of 7 parallel binaries (gpu lib, render lib
  x2, render acceptance, render template, tools lib; 70 runs, cap 600 s), 0 hangs and 0 timeouts,
  longest run 66 s (fixes agent, `target/agents/fixes/stress/results.txt`). `lifecycle::tests`
  (5 tests) cover the lock itself.
- **Limits.** Clones of `device` / `queue` dropped elsewhere are outside the lock, and a thread
  exiting during a creation is not stopped by it; the shared device closes that window after its
  first use. The render lib test binary still makes one device per module (deform, skin, compress,
  groom, `tests.rs`) and `crates/tools/src/bake/gpu.rs` its own; switching them to
  `shared_headless()` is proposed, not done. Unbounded waits remain in `ReadbackRing::read_blocking`,
  `compress/offline.rs` and some test helpers.
- Source: `target/agents/skin-shading/STATUS.md` (cause, render-test fix), `target/agents/fixes/STATUS.md`
  (proposed ADR, lifecycle lock).

## ADR-042: Strand shape runs on the GPU, root placement on the CPU; point counts are fixed per groom

- **Decision.** A groom's generated strands have a fixed control-point count (2..=32; guides
  2..=64), so the GPU keeps a strand in registers. Root placement (density map, hairline, guide
  weights, clumps) runs on the CPU, deterministic from the seed, and map values are sampled per
  strand at layout time (`GroomLayout` factors), not read as GPU textures. The shape modifiers run
  on the GPU in three stages (shape; clump, collision and the f16 store; attach per frame), each with
  a CPU reference (`humanart_model::hair::generate`, `humanart_render::groom`, `shaders/groom/`).
  Hair absorption follows pbrt's convention (`sigma_a` per unit path length in fibre radii,
  `T = exp(-sigma_a 2 cos(γt) / cos(θt))`); the hair shading of WP-18 must use the same.
- **Consequences.** Guide edits are GPU work (regenerate 1.14 ms GPU at 100 000 strands); density,
  mask and count edits rerun the CPU placement (337 ms for 100 000 strands in the optimised test
  profile, plus 11.8 ms layout upload). The per-strand melanin / dye `sigma_a` is computed on the
  CPU (`HairColor::strand_sigma_a`); the GPU groom does not output it.
- Source: `target/agents/hair/STATUS.md` (design notes / proposed ADR).

## ADR-043: Expression targets are generated from names; jaw and tongue are skeleton-driven

- **Decision.** The expression targets of the no-data template `[EXP-01]` are procedural
  (`humanart_model::expression::recipes`): each is built from the names of landmarks, joints,
  regions and parts with geodesic falloffs; left and right come from a smooth midline split, so
  left + right equals the bilateral target exactly. Jaw and tongue are driven by the skeleton
  (`data/template/expressions/drivers.json`); their targets are rest-space residuals against LBS /
  DQS. Every plain target gets an f16-aware local fold repair, because deltas are stored as f16 and
  thin triangles can flip by rounding.
- **Consequences.** All amounts, angles and gains are authored model choices, not measurements
  (B-001). The registry has no viseme controls, so `rig.json` adds seven `viseme.*` controls
  `[EXP-01]`; registry expression parameters map one to one to rig controls.
- Source: `target/agents/expression/STATUS.md` (proposed ADRs).

## ADR-044: Skin subsurface scattering uses one profile width per pixel and a tangent-plane edge test

- **Decision.** The skin diffusion of WP-14 (`humanart_render::sss`, `shaders/render/sss.wgsl`,
  `shaders/render/subsurface.wgsl`) uses the d'Eon & Luebke six-Gaussian three-layer profile. The
  separable passes (`Review` and `Still` quality; 25 taps, quadratic offsets over ±8.2 mm) scale the
  kernel by one profile width per pixel (`SkinShading::scatter_scale`, set from the pigment model's
  radii); the per-channel shape is the measured profile's. A tap counts as the same surface by a
  tangent-plane test (the distance of its depth from the centre's plane along the view, 3 mm x
  scale, fading over 3 mm), with one filtered fetch per tap and no per-tap normal or G-buffer fetch.
  `Interactive` quality has no separable passes and uses the pre-integrated table (Penner) with
  curvature from `fwidth`. Translucency takes its thickness from the shadow maps only.
- **Reason.** The 1440p budget (1.2 ms): one fetch per tap took the passes from 1.34 ms at 33 %
  skin coverage to 0.83 ms at 58 %.
- **Consequences.** `[SHD-02]` asks for "normal-aware weights"; the tangent-plane test is the
  normal-aware part, not a per-tap normal comparison. The pigment model's per-channel radii set only
  the mean width. The baked thickness map `[BAKE-01]` is not used yet.
- Source: `target/agents/skin-shading/STATUS.md` (reported as a simplification).

## ADR-045: LOD budgets are enforced per collapse by measurement; every level is a valid UV layout

Amends ADR-021.

- **Context.** On the generated template the LOD generator stopped at 71 / 60 / 48 / 47 % of the
  triangles instead of 50 / 25 / 12 / 5 % (`[MOD-05]`). The lod-fix agent's census
  (`mod_05_template_census`) showed that locked junction vertices were not the limit: without the
  bisection the run reached every target, but the run's error estimates did not bound the measured
  errors (a collapse also changes the triangles that vertices merged into the neighbours of the
  removed vertex project on), so the bisection rolled back the whole tail of each level. The worst
  skin-weight errors were finger vertices measured against the next finger's triangles, lip corners
  and canthi.
- **Decision.** Before a collapse is kept it is made on the topology, and every LOD0 vertex whose
  measurement candidates it can change (merged into the kept vertex, its neighbours, or the
  neighbours of the removed vertex's former neighbours) is measured exactly as the report measures
  it (`report::vertex_error`), with a per-LOD0-vertex cache (nearest triangle and distance) so only
  affected vertices are re-measured. A collapse over a budget is undone and refused for that level
  (`refused_collapses`). The bisection rollback of ADR-021 stays as a safety net. Geometric and
  attribute measurement candidates are restricted to triangles with a corner in the vertex's own
  region (no finger-to-finger projection); this is still an upper bound of the validator's distance.
  Every level must be a valid template on its own: UV triangles a collapse changes keep their
  orientation and a twice-area of at least 4e-7, and must not overlap another live triangle of their
  tile (`simplify/uvgrid.rs`, insert-only grid plus SAT test); LOD0 polygons that contain a UV-sliver
  triangle keep their corners and are emitted whole.
- **Evidence.** `mod_05_generated_template_meets_level_targets` (ignored, release; the lead reran it
  in round 5: all four levels pass): ratios 0.500 / 0.250 / 0.120 / 0.050 within the default budgets
  (geometry 0.5 / 1.5 / 4 / 10 mm, skin L1 0.1 / 0.2 / 0.35 / 0.5), every level validates as a
  standalone template, 0 collapses undone by the bisection. Numbers in `docs/perf-deviations.md`.
- **Consequences.** Verification and the UV grid cost about 2x on the 100k cube-sphere benchmark
  (12.0-19 s under load, against 6.35 s measured before). 360 vertices stay locked because they are
  corners of LOD0 quads containing a UV-sliver triangle (e.g. inner canthi); the template generator
  could remove those slivers. No part (e.g. teeth) is dropped at far levels: `[MOD-05]` keeps regions
  and seams, and the targets are met without it.
- Source: `target/agents/lod-fix/STATUS.md` (proposed ADR, census, measurements).

## ADR-046: Body proportions come from the ANSUR II summary file

- **Context.** ADR-039 asks that the template's proportions come from published anthropometry with
  the source recorded; `crates/model/src/generate/anatomy.rs` holds values transcribed from memory.
- **Decision.** The template's body measurements and the identity axes' means, SDs, percentiles and
  correlations are read from, or generated against, `data/anthropometry/ansur2.json`. That file is
  rebuilt only by `tools/anthropometry/ansur2_summary.py` from the publisher's CSVs (both SHA-256 are
  recorded in the file; the lead's rebuild from the downloaded CSVs was byte-identical). Constants in
  code that claim an ANSUR value cite the variable id and agree with the file to the stated
  rounding; whether a test compares them is template-gen's call.
- **Licence wording.** The publisher's own words are used, not "public domain": the US Army
  Memorandum for Record RDNS-SEW-THA (14 April 2017) says the databases were "cleared for UNLIMITED
  PUBLIC RELEASE", and report NATICK/TR-15/007 (Gordon et al. 2014) says "Approved for public
  release; distribution is unlimited". Neither document says "public domain"; the hosting page
  (OPEN Design Lab) states no terms of its own. Only aggregates are stored, no per-subject rows.
- **Population bias** travels with the numbers: US Army soldiers measured 2010-2012 (4082 men,
  1986 women, age 17-58), a working-age, physically active, screened military population. The
  memorandum says combining the male and female databases "will result in a sample that is not
  representative of any real population". The template stays a sex midpoint (ADR-039) as a design
  choice; identity axes should model the two sexes separately (per-sex mean, SD, correlation) and
  interpolate. Ranges outside the population (children, the elderly, very high BMI) are
  extrapolation and need another source before they are claimed.
- **Face.** Proportions ANSUR II does not cover use the NIOSH 2003 head-and-face survey (Zhuang &
  Bradtmiller 2005; the CDC Stacks record lists it as Public Domain) where it measures the same
  thing; vertex-menton (`HEAD_HEIGHT`) and eye placement remain unsourced until an open source is
  found.
- **Consequences.** `anatomy.rs` must drop "transcribed from memory" and its wrong per-sex numbers;
  the constants the anatomy-data agent flagged (more than 1 % from the sex midpoint, e.g. upper arm
  -23 mm, hip joint height +32 mm, crotch height -19 mm, neck base -27 mm) are corrected or
  documented as deliberate deviations (template-gen). The public data has no body-fat measurement,
  and ANSUR waist is at the navel, not the WHO site.
- Source: `target/agents/anatomy-data/STATUS.md` (proposed ADR, licence quotes, comparison table).

## ADR-047: Skin colour is calibrated against ISSA, with packaged eumelanin

- **Context.** `[SKN-10]` / `[AC-WP13-1]` need measured reference swatches (B-006). The skin-finish
  agent found the homogeneous pigment model far too yellow at mid and high melanin compared with
  ISSA (b* 2-4x the measured mean below L* 50).
- **Decision.** The `[AC-WP13-1]` reference is the International Skin Spectra Archive: Lu Y. et al.
  2025, "The International Skin Spectra Archive (ISSA): a multicultural human skin phenotype and
  colour spectra collection", Scientific Data 12, 487, doi:10.1038/s41597-025-04857-5; data figshare
  doi:10.6084/m9.figshare.28228571.v4; CC BY 4.0. It is summarised (aggregates only) by
  `tools/skin-reference/gen_skin_reference.py` into `data/test-scenes/skin-reference.json`, binned by
  ITA category, L* band and body site. In `crates/model/src/skin_appearance/pigment.rs` eumelanin
  absorption is flattened by the Duysens (1956) packet law `(1 - e^{-σ s}) / s` applied to the
  Donner & Jensen 2006 coefficient, with an effective packet path `s` of 0.035 mm and the melanin
  fraction range raised from 0..0.5 to 0..1, both fitted on a grid to ISSA; pheomelanin stays
  homogeneous. The absorption spectra stay the published ones. Packaging is linear in
  concentration, so it lives in the GPU band table and `shaders/skin/resolve.wgsl` is unchanged. The
  comparison adds the instrument's specular component (Fresnel at n = 1.4, 0.0278), because ISSA is
  specular-included and the model's albedo is not.
- **Why.** The measured apparent melanin optical density flattens with darkness (OD(400)/OD(700):
  13 for very light, 2.4 for dark skin), which a homogeneous absorber cannot do. Before the change
  the ITA bin means were off by ΔE00 up to 5.56 (dark), after it 0.00; worst decile-edge swatch 7.83
  before, 2.14 after (numbers in `docs/perf-deviations.md`).
- **Alternatives.** Hand-tuned melanin spectra (no provenance); an additive upper-epidermis
  reflectance term (cannot reach the dark bin); packaging both melanins (drives the eumelanin share
  to 0 for light-to-brown skin); per-texel non-linear packaging (needs a shader change; not tried).
- **Open questions for the owner (not settled).** (1) ISSA records no Fitzpatrick phototype, so the
  "Fitzpatrick I-VI" coverage of `[SKN-10]` / `[AC-WP13-1]` is read as the six ITA categories
  (Chardon 1991 / Del Bino 2006). (2) The spec gives no ΔE tolerance; the tests use ΔE00 <= 1.0 for
  every bin mean, <= 2.5 for the 36 decile-edge swatches and spectral RMS < 0.035 per ITA bin, and
  the edge and RMS bounds were set by the agent after seeing the results.
- **Limits.** The packet path is an effective parameter, larger than a melanosome. A three-parameter
  fit (melanin, eumelanin ratio, haemoglobin) to three coordinates makes bin means easy, so the edge
  swatches and the spectral RMS are the stronger evidence. Haemoglobin packaging in vessels is not
  modelled (the light-skin spectral residual). Groups beyond ISSA's eight are not represented.
- Source: `target/agents/skin-calib/STATUS.md` (proposed ADR, measurements);
  `target/agents/skin-finish/STATUS.md` (first check against ISSA; its citation "Yan et al." is
  corrected to Lu et al.: Crossref lists the first author with family name Lu, given name Yan).

## ADR-049: Template skin weights are authored procedurally

- **Context.** `[SKIN-01]` makes skin weights authored data in the template. No scan data exists
  (B-001), so the generated template's weights cannot be fitted.
- **Decision.** `generate::rig::skin` authors them: per-region rules (inverse-distance weights to
  bone segments; the jaw by height; eyelid helpers near the lid margin; the eyes rigid), 10 Laplacian
  smoothing steps on the welded body, then a continuous top-4 sparsification. Dual quaternion
  skinning for the neck, shoulders, forearms and palms (`[SKIN-01]` names wrists; the palms region
  covers them). Round 2 adds an axilla rule (`rig::axilla`, `blend_axilla`): below the shoulder the
  upper arm's share grows linearly with the angle about the shoulder in the frontal plane (0 at the
  chest wall, 1 at 0.78 rad), fading out above the arm axis, medially and beyond 0.14-0.24 m.
- **Evidence.** `mod_07_skeleton_and_skin_validate_and_pose` (validator passes, 0 seam mismatches,
  weight sums within 2e-7, the rest pose reproduces the mesh within 1e-5 m, skeleton mirrored);
  `skin_02_arms_come_down_to_the_sides_without_folding` (0 body faces turn over with the arms lowered
  0.5 and 0.65 rad). Template-gen's runs; inside the lead's humanart-model rerun (321 of 322 pass).
- **Consequences.** Plain LBS still folds the side of the chest when an arm swings toward the body,
  and the open jaw stretches the submandibular skin (no pose correctives yet). The weights are to be
  replaced by fitted ones once scan data exists.
- Source: `target/agents/template-gen/STATUS.md` (proposed ADR; round 2 armpit rule).

## ADR-050: The generated template is mirror-exact; asymmetry comes only from components

- **Context.** `[ID-05]` makes asymmetry an explicit set of components. Side-dependent construction
  in the generator (fan starts, ring orientation, region tags taken from a ring's first slot) had
  produced left/right differences, e.g. the two mouth corners in different regions, moving up to
  9 mm differently with the jaw open.
- **Decision.** Topology, rest positions, parts and regions of the generated template are exact
  mirror images (x -> -x). Asymmetry enters only through the `[ID-05]` components (ADR-048). No
  symmetry map is stored in the package: a vertex's mirror is the vertex at the mirrored position.
  One deliberate exception: the nose's tip / ala / bridge region split stays side-dependent, because
  a mirror-exact split trips identity's `id_02` nose-length check (documented in `face::nose`,
  excluded in the test).
- **Evidence.** `mod_01_surface_and_parts_are_mirror_symmetric` (surface max 0.005 mm, parts
  0.0005 mm), `mod_03_body_regions_are_mirror_symmetric`, landmark L/R max 0.000 mm
  (`mod_06_landmarks_are_valid_symmetric_and_documented`), a posed-jaw mirror check (0.005 mm).
- **Consequences.** Making the mouth-corner regions mirror-exact changed the expression sweep, which
  now fails by small margins, equally on both sides (row 19). Mirror tools (`[TOOL-01]`,
  `[AC-WP20-3]`) can compute the vertex map once at load.
- Source: `target/agents/template-gen/STATUS.md` (proposed ADR; round 2 region fix).

## ADR-051: Calibrated identity axes move their ANSUR II measurement by one SD per unit

- **Context.** ADR-046 makes `data/anthropometry/ansur2.json` the source of measurement statistics;
  the authored identity components of round one had arbitrary amplitudes.
- **Decision.** `identity::measure` measures the template like a tape (landmark paths, heights,
  breadth and depth over a band of regions, convex-hull girths) and scales each calibrated axis by
  bracketed bisection so that weight 1 moves its one ANSUR variable by one SD, taken as the RMS of
  the male and female SDs. 14 axes are calibrated: height, leg and arm length, shoulder, hip and
  waist width, glute size, thigh fullness, palm width, foot length and width, eye spacing, ear size,
  neck width. `global.mass` is a least-squares fit to the expected waist / chest / buttock / thigh
  girth change per SD of weight at fixed stature (partial regression from the file's correlations);
  `global.sex` scales its shoulder, hip, waist and neck terms so that +-1 is the male / female mean
  relative to stature. Breast, nipple, areola, hip flank, muscularity, age, fingers and most of the
  face stay authored and uncalibrated. The sex axis is zero in an ellipse around the crotch, so the
  discrete genital variant (ADR-039) never moves with it. `[MOD-07]`: each component's knee, ankle,
  elbow and wrist joint offsets are the mean displacement of their skin landmark rings
  (`space::SKIN_RINGS`), so the regressor rows follow the authored shapes; they are not fitted to
  data (B-001).
- **Evidence.** `id_03_calibrated_axes_move_their_measurement_by_one_sd` (all within 0.1 %),
  `id_03_ansur_constants_match_the_data_file`, `id_03_sex_axis_leaves_the_groin_and_genital_parts_alone`,
  `mod_07_joints_follow_the_shape` (8 rings), `id_02_body_shapes_have_no_stepped_falloff`. Mass at the
  agent's run: 97 / 60 / 101 / 52 mm against 106 / 84 / 76 / 58 mm expected; sex: hips about 25 %
  over (the authored flank and buttock terms add to it).
- **Deviation from ADR-046, not settled.** ADR-046 says identity axes "should model the two sexes
  separately (per-sex mean, SD, correlation) and interpolate"; one pooled RMS SD per axis does not.
- Source: `target/agents/identity/STATUS.md` (round two; it proposed no ADR, this records the design
  as built).

## ADR-052: Surfaced skin reads the compositor's resolved set at group 3 of the geometry pass

- **Context.** The compositor (ADR-036), the micro-detail exemplar (ADR-037) and wrinkle blending
  existed, but the skin shading pass did not use them, and `[SHD-06..09]` were missing (row 14).
- **Decision.** One "skin surface" bind group at group 3 of the geometry pass
  (`humanart_render::surface::SkinSurface`, library `shaders/render/skin_surface.wgsl`) holds the
  resolved set, specular and zone-mask arrays, the micro-detail exemplar as mip-mapped slopes
  (`shaders/render/detail_mips.wgsl`), the wrinkle maps, activations and tile slots, and per-UV-tile
  mm per UV. Objects opt in with `SkinShading::surface`; 1x1 neutral defaults are bound otherwise.
  Sampling uses explicit LODs (`textureSampleLevel`, one LOD per texture set; 0.2 ms cheaper than
  `textureSampleGrad`); UV tiles are in the integer part of u (`Mesh::from_template`); tangent frames
  come from screen derivatives; micro-detail slopes are blended with the variance-preserving operator
  and the filtered-out slope variance is added to GGX alpha² (LEAN-style). With no authored Langer
  field on the template, the line direction defaults to circumferential about the object's up axis.
- **Choices made on the way.** Vellus zones are cheeks, nose and ears (the forehead stays at the
  35 % baseline); the sheen has no environment term; coat f0 0.03; baked thickness enters the
  compositor as a byte in 0.1 mm units (255 = none), while the `[BAKE-01]` baker writes metres as f32
  and nothing converts it yet; the SSS width per pixel is the mean resolved scattering radius over
  the profile's mean RMS radius.
- **Evidence.** `crates/render/tests/surface.rs`: `skn30_folded_wrinkle_bends_the_shading_normal`,
  `skn20_micro_detail_follows_the_skin_lines_not_the_uvs` (variance across / along the lines 2.04x,
  the same with UVs rotated 90 deg), `skn01_surfaced_template_stills`,
  `perf_surfaced_skin_geometry_at_1440p` (deviation D-006 in `docs/perf-deviations.md`).
- Source: `target/agents/skin-render/STATUS.md` (proposed ADR).

## ADR-053: Blood is packaged per haemoglobin species with the vessel factor

Amends ADR-047.

- **Decision.** In `skin_appearance::pigment` each haemoglobin species (oxy, deoxy) is packaged
  separately with the vessel correction factor `C = (1 - e^{-2 μa r}) / (2 μa r)` (Verkruysse et al.
  1997, Phys. Med. Biol. 42:51-65, in the form of van Veen, Verkruysse & Sterenborg 2002, Opt. Lett.
  27:246-248: the Duysens law with path 2r), so the GPU band table stays linear in blood fraction and
  oxygenation (no shader change). `Mapping::blood_vessel_radius_mm` = 0.013 mm, fitted on a grid to
  ISSA (radius 0..0.02 mm with the eumelanin packet 0.03..0.04 mm; the packet stays 0.035 mm).
- **Evidence.** `pigment` tests (15 pass at the agent's run, 2 new, among them
  `ac_wp13_1_blood_packaging_flattens_the_light_skin_spectra`): spectral RMS per ITA bin very light
  0.0268 -> 0.0072, light 0.0308 -> 0.0082, intermediate 0.0262 -> 0.0081, tan 0.0189 -> 0.0064,
  brown 0.0112 -> 0.0047, dark 0.0076 -> 0.0065; worst bin-mean ΔE00 0.60 -> 0.81 (tolerance 1.0),
  worst decile edge 2.14 -> 1.86 (tolerance 2.5). The RMS tolerance was tightened from 0.035 to
  0.012, again after seeing the results (the owner question of ADR-047 / B-006 covers it). Packaging
  the species separately differs from packaging the mix by up to 11.1 % per band, colour ΔE00 <= 0.336.
- **Consequences.** The light-skin spectral residual listed under ADR-047 "Limits" is gone.
  `docs/shader-notes.md` "Skin pigment model" now describes the packaged model.
- Source: `target/agents/skin-wire/STATUS.md` (proposed ADR and provenance row).

## ADR-056: The scan-derived face model is published under HSRD-100's CC BY 4.0

- **Context.** The default face (`data/template/face/face-model.hafm`, todo 1.1) is derived from 8
  HSRD-100 scans. The dataset card on Hugging Face licenses the dataset CC BY 4.0; each scan's own
  metadata carries `"license": "Commercial"` and a price. The file was kept out of the repository
  until this was settled, which left a fresh clone unable to compile `humanart-model` (it embeds the

- **Decision.** Publish the file under CC BY 4.0 with attribution. Reasons: the licensor published
  this dataset on Hugging Face with CC BY 4.0 as its stated licence (card front matter and text, its

  (HumanScanRepository), where the same scans are sold, and does not override the licence chosen for
  this release; a CC licence cannot be revoked for material received under it. CC BY 4.0 allows
  sharing adapted material, commercially too, with credit, a link to the licence and a note of the

- **Consequences.** A clone builds and gets the same face. If the licensor ever states that the
  per-scan terms govern, the file is replaced by one built from openly licensed scans (or the
  procedural face, `scan_face: false`) and this ADR is revisited.

## ADR-057: Pose correctives are solved by radial basis interpolation and derived from better skinning

- **Context.** `todo.md` 1.3 asks for pose correctives at the shoulders, armpits, elbows, hips and
  knees. A `PoseCorrective` fades in around one target rotation with a compact kernel, which is
  weakest where one joint reaches the same skin through very different rotations: two overlapping
  kernels both switch on half way and add up. The template had no correctives at all, so the
  default (linear-blend) skinning collapsed the bent elbow and knee (the 126-degree knee lost
  709 cm³) and turned faces over at the raised shoulder.
- **Decision.** (1) A `PoseDriver` (`humanart_model::expression::pose_space`, section `PDRV` of the
  package, written only when a template has drivers) groups the correctives of one joint and
  solves them by Gaussian radial basis interpolation over their target rotations with the rest
  pose as an implicit zero example, comparing the swing, the unwound twist about the bone (the
  joint frame's Y) or the whole rotation; activations are clamped to [0, 1] and scaled down when
  they sum above 1. It follows OpenRigLogic's interpolative solver and swing/twist metrics (MIT,
  Epic Games; the notice is kept in the module). `PoseSpace` evaluates every corrective (drivers and
  free kernels) without allocation and is shared by the CPU evaluator and the GPU deformer, so
  both activate identically. (2) The template's correctives (`generate::correctives`, 11 example
  poses per side: elbow 90 and 140 degrees, knee 90 and 126, shoulder down, up, forward, back,
  hip flexed, extended, spread) are derived, not sculpted: the rest-space delta that turns the
  default skinning into a target surface at the example pose. The target is dual-quaternion
  skinning (hips) or Delta Mush (Mancewicz et al. 2014) of it with the enclosed volume put back
  around the bent joint (elbow, knee, shoulder), chosen by measurement (volume, faces turned over,
  mean change of the dihedral angles near the joint) against the alternatives (plain Delta Mush,
  10 to 40 iterations, with and without the volume, dual quaternions alone).
- **Alternatives.** Sculpted corrective shapes (none exist, and nobody here can sculpt and judge
  them on screen); optimised centres of rotation (Le and Hodgins 2016), a skinning method rather
  than correctives and an O(vertices × triangles) precomputation; per-pose Delta Mush at run time
  (smoothing every frame breaks `[PERF-R1]`).
- **Consequences.** Posed bodies keep their volume at the knee and elbow and fold less at the
  shoulder (test `todo_1_3_correctives_keep_volume_and_smooth_folds_at_bent_joints`; numbers in
  `todo.md` 1.3). Past about 126 degrees the calf meets the thigh: there is no contact handling, so
  the deepest knee example stops there, and the elbow at 140 degrees still has about 160 faces
  turned over in the crease where the arm folds on itself. The shapes are a starting point the
  sculpt tools can refine; twist joints (`upper-arm.twist`, `forearm.twist`) still carry no skin
  weights, so a rolled forearm still wraps.
- Source: the lead, 2026-11-23 (todo 1.3, overnight run).
